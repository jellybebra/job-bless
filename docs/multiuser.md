# Несколько пользователей: Clerk и личные рабочие среды

`compose.multiuser.yml` запускает общий вход Clerk. После регистрации пользователь
получает собственный экземпляр приложения: SQLite, резюме, вакансии, оценки,
сопроводительные письма, отклики, настройки, журналы, расписания и сессии браузеров.
Одинаковые ID вакансий и резюме у разных пользователей не пересекаются.

Clerk отвечает за регистрацию и вход в job-bless. Входы в HH и Google AI Studio
каждый пользователь выполняет отдельно в своих удалённых браузерах.
Выход из Clerk закрывает доступ к панели и экранам; запущенный сбор и расписание
продолжают работать на сервере.

## Запуск

Нужны Linux Docker Engine или Docker Desktop в режиме Linux, готовые образы
приложения, HH и Google, а также приложение Clerk. Секретный ключ передаётся только
серверу. Для постоянной публичной установки используйте production instance Clerk;
ключи `pk_test_` / `sk_test_` включают development mode и его ограничения.

Пример `.env` (не добавляйте этот файл в Git):

```dotenv
COMPOSE_FILE=compose.multiuser.yml:compose.traefik.yml
COMPOSE_PROJECT_NAME=job-bless
GATEWAY_CONTAINER=job-bless-gateway
SITE_DOMAIN=jobs.example.com
WEB_PUBLIC_URL=https://jobs.example.com
CLERK_PUBLISHABLE_KEY=pk_live_REPLACE
CLERK_SECRET_KEY=sk_live_REPLACE
WORKSPACES_HOST_ROOT=/opt/job-bless-workspaces
JOB_BLESS_IMAGE_PREFIX=ghcr.io/jellybebra/job-bless
JOB_BLESS_IMAGE_TAG=sha-REPLACE
```

`WORKSPACES_HOST_ROOT` — абсолютный путь именно на хосте Docker. Gateway видит
эту папку как `/workspaces` и создаёт внутри каталоги с непрозрачными ID.
Не подключайте её к пользовательским контейнерам целиком.

Сначала скачайте все три образа **одной версии** (`-app`, `-hh`, `-aistudio`), затем:

```bash
docker compose up -d --wait
```

`compose.traefik.yml` требует работающий Traefik в сети `traefik-public`.
Для локальной проверки используйте только `compose.multiuser.yml`, задайте
`WEB_PUBLIC_URL=http://localhost:18743`, `WEB_PORT=18743`, `WEB_BIND=0.0.0.0`.
Чтобы вход работал по адресу в локальной сети, укажите этот адрес вместо localhost
в `WEB_PUBLIC_URL` и открывайте приложение по нему: проверка Origin намеренно точная.

## Изоляция и жизненный цикл

Gateway проверяет подпись RS256, issuer, срок действия и Origin (`azp`) токена Clerk,
а также статус сессии через Backend API. Имя рабочей среды определяется только
проверенным `sub`; клиентские служебные заголовки удаляются. Изменяющие запросы
проверяют Origin и индивидуальный CSRF-токен. Выгрузки CSV, SSE и WebSocket экранов
проходят через ту же авторизацию. Отзыв сессии проверяется каждые 15 секунд.

У каждой среды отдельные контейнеры и отдельная Docker bridge network. Пользовательские
контейнеры не публикуют порты, не имеют Docker socket и видят только собственные
каталоги данных. Лишь доверенный gateway имеет доступ к Docker для запуска фиксированных
образов и маршрутизации запросов. Режим предназначен для одного доверенного сервера.

Приложение запускается при первом обращении, браузеры — при входе или задании, которому
они нужны. Ожидание запуска одного пользователя не блокирует остальных. Через 30 минут
без запросов среда останавливается, если в ней нет задач, открытых экранов или включённых
расписаний. Данные и входы сохраняются. Расписания работают и при закрытом браузере
пользователя. Перезапуск gateway сохраняет работающие среды; новая версия образа
обновляет их. Нагрузка на память зависит от количества одновременно работающих
браузеров: ресурсы сервера нужно увеличивать вместе с числом активных пользователей.

Лимит контейнера HH — 2 ГиБ: 1 ГиБ недостаточно для тяжёлой выдачи HH и может
привести к аварийному закрытию вкладки. Сбор повторяет загрузку текущей страницы
после сбоя браузера, сохраняя уже обработанные страницы и вакансии. Пауза между
попытками увеличивается до 30 секунд; кнопка «Стоп» работает и во время ожидания.
Ошибка загрузки не считается пустой выдачей или успешным завершением поиска.

## Перенос личной установки

1. Остановите прежний экземпляр, чтобы сохранить сессии и получить согласованную копию.
2. Сделайте резервную копию БД, каталога данных, Docker volumes `hh-profile` и
   `google-data`, а также прежнего `.env`.
3. Подготовьте в `WORKSPACES_HOST_ROOT/legacy` три каталога:
   `app` — прежний каталог приложения (БД и `hh-session.json`),
   `hh` — содержимое volume `hh-profile`, `google` — содержимое volume `google-data`.
4. Укажите `CLERK_OWNER_EMAIL` — email владельца прежних данных — и запустите gateway.

Данные будут привязаны один раз к Clerk user ID с **подтверждённым** адресом владельца
при его первом входе. Первый произвольный зарегистрировавшийся пользователь их не
получает. Остальные аккаунты начинают с пустой системы. После привязки смена email
не меняет владельца. Каталог `legacy` остаётся резервной копией; удалять его можно
после проверки переноса и создания отдельной резервной копии.

Резервируйте весь `WORKSPACES_HOST_ROOT`, включая `workspaces.db`: там хранится привязка
Clerk user ID к данным и приватные ключи рабочих сред. Для согласованной копии сначала
остановите принадлежащие этой установке контейнеры пользователей. Остановка только
gateway не останавливает фоновые задания. Удаление или блокировка аккаунта в Clerk
отзывает доступ; периодическая проверка останавливает его рабочую среду и расписания.
Пользовательские данные с диска автоматически не удаляются.

## Совместимость

`docker-compose.yml`, локальный запуск и Windows-комплект сохраняют прежний личный
режим с паролем/локальной ссылкой. Для них Clerk и многопользовательский gateway не нужны.
